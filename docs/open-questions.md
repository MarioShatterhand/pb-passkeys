# Open questions and assumptions

Each item must be resolved (verified in the pinned PocketBase source, or decided by a maintainer) before the related feature is implemented. Update this file when an item is closed: move it to "Resolved" with the answer and the PocketBase version it was checked against.

## Assumptions still open

1. **Argon2id cost on a small VPS.** Measured on a development workstation (one core, about 5 GHz, Go 1.27.4): 64 MiB / t=3 / p=1 takes about 76 ms and allocates 64 MiB per verification. A 1 vCPU VPS is slower by an unknown factor, so the target (under 300 ms per verification) is plausible but **not yet measured on target hardware**. With `MaxConcurrentHashes: 2` the peak is about 128 MiB plus Go runtime overhead, which is tight on a 512 MB instance. To do: ship a benchmark (`go test -bench Argon`) and measure on a 1 vCPU / 1 GB VPS before 0.2.

## Decisions open for maintainers

1. **npm package name** for the client. Proposed `pb-passkeys`; availability on npm not yet checked.
2. **Client dependency.** Proposed zero dependencies. Alternative: depend on `@simplewebauthn/browser` (mature, but another package on the login path).
3. **Non-discoverable login.** Logging in with an `identity` returns that user's `allowCredentials`, which reveals whether the account exists and how many keys it has. Proposed for v0.x: not supported; `ResidentKey` only accepts `Required`. Later option: for unknown identities return deterministic fake `allowCredentials` derived with HMAC from a server secret, which needs a stored per-installation key.

## Resolved

- **Project name: pb-passkeys.** Go module `github.com/MarioShatterhand/pb-passkeys`, package `passkeys`, under the maintainer's personal GitHub account. (Decided 2026-11-22.)
- **License: MIT**, matching PocketBase. `LICENSE` is in the repository. (Decided by the maintainer, initial commit.)
- **Contributor sign-off: DCO** (`Signed-off-by`), no CLA. Required in CONTRIBUTING.md and CLAUDE.md.
- **Route prefix: `/api/passkeys/{collection}/...`** (configurable through `RoutePrefix`). The alternative under `/api/collections/` was rejected because it could clash with future PocketBase routes. (Decided 2026-11-22.)
- **User handle: the PocketBase record ID.** It is random and carries no personal data. A separate rotatable handle was rejected for v0.x because it needs extra storage. (Decided 2026-11-22.)
- **Passkeys and PocketBase MFA: PocketBase's behaviour is kept.** The module always passes the method name `"passkey"` to `RecordAuthResponse`. If a collection has MFA enabled, PocketBase answers a passkey login with 401 and an `mfaId` and asks for a second, different method. A passkey with user verification is already two factors, so the documentation recommends MFA **off** for collections that use passkeys. There is no setting to skip MFA: the only way would be an empty method name, which also drops the new-device login alert. (Decided 2026-11-22.)
- **Collection names are fixed after the first start.** The module's migration creates its collections under the names in `Config.Collections` at the time it first runs. The module does not rename them later; at startup it fails with a clear error if a configured collection is missing. To rename, the application renames the collections itself and updates the config. (Decided 2026-11-22.)

### Verified in source (PocketBase v0.40.6, go-webauthn v0.18.2, checked 2026-11-22)

- **Migrations from a library: confirmed, with conditions.** `core.AppMigrations` is a package-level list; `Register(up, down, optFilename)` appends to it and keeps it sorted by file name. `apis.Serve` and `tests.NewTestApp` call `RunAllMigrations`, which runs system migrations, then all app migrations in file-name order, in one transaction, skipping names already in `_migrations`. Consequences: the module must pass an explicit, globally unique file name (the default is the base name of the calling `.go` file, which could collide with an application's file); ordering against the application's migrations is by name only, so the module's migration must not depend on application collections (it does not: owners are referenced by text fields); registration must happen before `app.Start()`. (`core/migrations_list.go`, `core/migrations_runner.go`, `core/base.go`, `apis/serve.go`)
- **Auth response: confirmed.** `apis.RecordAuthResponse(e, record, authMethod, meta)` is exported. It creates the token, checks the collection's `AuthRule` against the record, triggers `OnRecordAuthRequest`, runs the MFA check, records the origin in `_authOrigins` and sends the new-device alert when `AuthAlert` is enabled and `authMethod` is not empty. (`apis/record_helpers.go`)
- **MFA interplay: confirmed, differs from the expectation.** The method name is a free string; `core` defines only `password`, `oauth2`, `otp` as constants. If the collection has MFA enabled (and its MFA rule matches), the first successful method gets HTTP 401 with `{ "mfaId": ... }` and the second request must use a **different** method name. An empty method name skips both MFA and the login alert. See the MFA entry above. (`apis/record_helpers.go`, `checkMFA`)
- **Session revocation: confirmed.** Tokens are signed with `record.TokenKey() + collection.AuthToken.Secret` and verified with the record's current key, so `record.RefreshTokenKey()` followed by a save invalidates every existing auth token of that record. Side effect: the same key signs verification, password-reset, email-change and file tokens, so pending ones stop working too. (`core/record_tokens.go`, `core/record_query.go`)
- **Passwordless users: confirmed.** `password` is a required system field of auth collections. PocketBase has `Record.SetRandomPassword()` for exactly this case (it is what the OTP and OAuth2 flows use for auto-created users): about 30 random characters, stored only as a hash, plain-value validators skipped, `tokenKey` refreshed. The module uses it instead of generating its own password. With `PasswordAuth.Enabled = false` the password login and password-reset request routes return an error. (`core/record_model_auth.go`, `apis/record_auth_with_password.go`, `apis/record_auth_password_reset_request.go`)
- **Rate limiter: confirmed.** A global rate-limit middleware is bound to the whole router, so custom routes are covered. A rule label can be a tag, an exact path, or a path prefix ending in `/`, optionally with a method (`POST /api/passkeys/`); wildcards inside a path are not supported, so a rule cannot single out `{prefix}/{c}/login/` across collections, only a collection-specific prefix. Limits are keyed by `e.RealIP()` (correct only if trusted proxy headers are configured), and superusers and `ExcludedIPs` are exempt. The configuration is readable at startup through `app.Settings().RateLimits` (`Enabled`, `Rules`). (`apis/middlewares_rate_limit.go`, `core/settings_model.go`)
- **Token age: confirmed.** `security.NewJWT` adds only `exp` to the claims; there is no `iat`. Issue time cannot be derived reliably from `exp`, because the duration is configurable and tokens can be refreshed. The explicit step-up token stays. (`tools/security/jwt.go`)
- **BE flag: confirmed, go-webauthn enforces it.** `validateLogin` rejects an assertion whose BE flag differs from `credential.Flags.BackupEligible`, and rejects BE=0 with BS=1. This works only if the module stores the flag at registration and passes it back in the `Credential`. The invariant keeps its test. (`webauthn/login.go`)
- **Request logs: confirmed.** PocketBase logs the request URI including the query string (up to 3000 characters), method, status, `Referer`, `User-Agent`, the auth collection (and the auth record ID and IPs if enabled), and for failed requests the error message and the `ApiError` data. Request bodies and other headers are not logged. So secrets in JSON bodies are safe, secrets in URLs would not be, and the module must never put a secret into an error message or `ApiError` data. (`apis/middlewares.go`, `logRequest`)

Found while verifying:

- **go-webauthn session expiry follows the browser timeout.** `SessionData.Expires` is set from the options' `Timeout`, and `Finish*`/`Validate*` reject an expired session. With `Timeout: 2 min` and `ChallengeTTL: 5 min` the challenge would effectively live 2 minutes. The module sets `SessionData.Expires` from `ChallengeTTL` itself and treats `Timeout` only as a hint to the browser.
- **Discoverable login requires a user handle in go-webauthn.** `ValidatePasskeyLogin` rejects an empty `userHandle` and calls the module's handler with `(rawID, userHandle)`; in `validateLogin` the handle is compared with the user's ID. The module's own check stays as defence in depth.
- **Sign counter never rejects in go-webauthn.** `Authenticator.UpdateCounter` only sets `CloneWarning` (and leaves the stored counter unchanged) when the counter does not increase and either value is non-zero. `SignCountPolicy` is implemented on top of `CloneWarning`.
- **Test app: confirmed.** `tests.NewTestApp()` clones a data directory into a temporary one, bootstraps the app and runs all migrations, including those registered in `core.AppMigrations`.
